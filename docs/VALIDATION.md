## Переключение между VPN Android — 0.3.3

Автоматическую передачу подключения выполняет Android через
[`VpnService.prepare()`](https://developer.android.com/reference/android/net/VpnService#prepare(android.content.Context)):
при ранее выданном согласии возвращается null, иначе запускается системный
экран разрешения. Это поведение уже использовалось клиентом; версия 0.3.3
добавляет обработку ошибок и повторную проверку после RESULT_OK.
При исключении или отказе ожидающий результат и конфигурация очищаются;
пользователь может повторить запуск. Для запросов выдаются разные activity
requestCode: запоздалый ответ отменённого запроса не завершает новый.
Закрытие Flutter engine также отменяет незавершённый запрос.

`onRevoke` теперь вызывает штатный STOP на главном потоке вместо перехода
в ошибку: отменяет startup, закрывает активный probe/API-запрос, освобождает
TUN и ядра, публикует disconnected. Приложение не пытается автоматически
отбирать VPN обратно у другого клиента без нового нажатия «Подключить».
Статические сообщения Dart поясняют отказ/недоступность разрешения и
настройки «Постоянная VPN»; приватные native exception details не передаются.

Регрессия: **368 passed, 164 deselected in 17.39s**, без тестов нативных
сетевых ядер. Отчёт: `build/regression-033.xml`, журнал:
`build/regression-033.log`. Настоящий Kotlin permission helper исполняется
на JVM с моделью Android: ранее выданное согласие, первый запрос, отказ,
повторная попытка, запрет политики/утрата права перед RESULT_OK, исключения
prepare/launch/start и отмена с запоздалым callback. Это проверка логики,
а не подтверждение отключения стороннего VPN на физическом устройстве.

Android SDK `adb devices -l` возвращает пустой список. На телефоне нужно
проверить: другой VPN → подключение Sever → возможное системное согласие →
Sever подключён, прежний VPN отключён; затем другой VPN → возврат в Sever.

## Уведомление Android VPN при длительной работе — 0.3.2

Предыдущее восстановление зависело от Handler главного потока и проверяло
только наличие записи в activeNotifications. `postDelayed` задерживается
во время deep sleep, как описано в [Android Handler](https://developer.android.com/reference/android/os/Handler#postDelayed(java.lang.Runnable,long)).
Без логов телефона конкретную причину исчезновения подтвердить нельзя.

медленных запросов к API VPN-ядра. Каждые две секунды проверяется отсутствие
уведомления, каждые 30 секунд оно публикуется повторно независимо от
activeNotifications. Интервал измеряется SystemClock.elapsedRealtime,
учитывающим время сна. Помимо startForeground вызывается NotificationManager.notify
с тем же ID и setOnlyAlertOnce; дополнительных уведомлений не создаётся.

уведомление сразу публикуется после пробуждения, без ожидания таймера.
Receiver удаляется при уничтожении службы, monitor отменяется при STOP/cleanup.
Wake lock, точные будящие alarms и дополнительные разрешения не добавлены.

Ошибки activeNotifications приводят к попытке публикации; неудачный post
не сдвигает время последнего успешного обновления и повторяется при следующей
проверке. Синхронизация с teardown сохраняется: после STOP запоздалые

## ECH через Xray и диагностика импорта — 0.3.1

Исправлен отказ «ECH через мост Xray пока не поддерживается».
Адаптер преобразует сохранённый sing-box PEM ECHConfigList в Base64-поле
Xray `tlsSettings.echConfigList` с `echForceQuery=full`. TLS SNI, fingerprint,
ALPN и gRPC serviceName/multiMode/authority остаются независимыми настройками;
исходный профиль не изменяется. Включённая TLS-проверка сохраняется.
Проверяется также ECH из сохранённых профилей: неверный PEM/Base64, отключённый
ECH и несколько конфигурационных блоков отклоняются безопасным сообщением.
Схема подтверждена по [исходникам Xray 26.3.27](https://github.com/XTLS/Xray-core/blob/v26.3.27/transport/internet/tls/ech.go).

Локальные тесты с настоящим Xray сгенерировали одноразовые ECH-ключи и
подтвердили передачу данных VLESS/Trojan gRPC через ECH для multi и authority,
включая автоматический выбор Xray при сохранённом предпочтении Mihomo.

клиент должен отказаться от передачи вместо перехода на обычный TLS.
Тесты Android bridge.connect проверяют ECH в документе, переданном нативной
службе. Полный Android TUN на устройстве этими проверками не моделируется.

В ходе проверки воспроизведена дополнительная Windows-проблема:
TCP-only выбор порта Xray мог попадать в зарезервированный UDP-диапазон,
после чего Xray завершался с ошибкой bind UDP. Случайные порты sidecar и
массового PROXY GET теперь проверяются для TCP и UDP, а заданные локальные
порты исключаются. Проверены повторный выбор при занятом UDP, исключение
порта и освобождение пробных сокетов. Исправлен также выбор портов тестовых
серверов, чтобы тесты не зависели от UDP-резервирований Windows.

Сообщения для неподдерживаемых схем теперь называют известный протокол
(например, VMess или Shadowsocks), а неверное форматирование ссылки
объясняется отдельно. Номера строк сохраняются; адреса и учётные данные

## gRPC и сборки Windows/Android — 0.3.0

Импорт VLESS/Trojan принимает gRPC `serviceName`, обычный `mode=gun`,

## Сохранение выбранного сервера после простоя — 0.2.6

Обновление подписки считало выбранный сервер удалённым, если изменялся
SHA-256 параметров подключения, и выбирало первый оставшийся профиль.
Старая реализация воспроизводит сброс в десяти новых регрессионных случаях.
Имена уже не входили в хеш; ротация пароля, UUID, Reality short ID, адреса,
порта, TLS или транспорта меняла ключ.

После проверки точного ключа обновление сопоставляет сервер только внутри
той же подписки: протокол + имя + адрес/порт, затем протокол + адрес/порт,
затем протокол + имя. Каждое совпадение должно быть единственным в старом
и новом списке. При удалении сервера или неоднозначности применяется
прежний выбор первого оставшегося профиля. Выбор берётся под блокировкой

## Android: отключение и пакетный путь TUN — 0.2.3

Подтверждена ошибка протокола отключения: плагин возвращал `disconnecting`
сразу после отправки STOP, а UI требовал уже завершённого `disconnected`.
Теперь MethodChannel ждёт отдельного IPC-подтверждения (what=11) после очистки
службы. Обычный снимок состояния, в том числе старый `disconnected`, не может
подтвердить STOP. Тайм-аут нативной операции — 35 секунд, Flet — 45 секунд;
неуспешный ответ сохраняет возможность повторить отключение.

STOP отменяет запуск и прерывает текущую HTTP-проверку. Перед ожиданием
закрытия libbox освобождается Android-дескриптор TUN, снимается сетевой callback.
Порядок соответствует [остановке upstream Android-клиента](https://github.com/SagerNet/sing-box-for-android/blob/dev/app/src/main/java/io/nekohasekai/sfa/bg/BoxService.kt).
В libbox дескриптор [дублируется](https://github.com/SagerNet/sing-box/blob/v1.14.0/experimental/libbox/service.go),
поэтому служба отдельно закрывает свой экземпляр и нативное ядро.

Для Android общий TUN sing-box/Xray/Mihomo использует `gvisor` вместо `mixed`,
чтобы TCP обрабатывался в пользовательском стеке. Явно заданы `dns_mode=hijack`
и адрес DNS `172.19.0.2`; удалённый DNS сохраняет detour через VPN.
Семантика DNS соответствует [sing-box 1.14 TUN](https://sing-box.sagernet.org/configuration/inbound/tun/).
Выбор начальной физической сети учитывает INTERNET и предпочитает текущую
активную сеть; повторный callback той же сети не сбрасывает соединения.
На Windows настройка стека TUN остаётся прежней.

## Исправление DNS-bootstrap Windows TUN 0.1.3 — 07.10.2026

обращении Xray к `1.1.1.1:53`: Windows TUN с `strict_route` и стандартным
`dns_mode=hijack` блокирует порт 53 на физических интерфейсах. Правило

результат обновляется при каждом подключении. В случае DNS-ошибки или таймаута
TUN не запускается, сообщение указывает на Bootstrap DNS. Отмена останавливает
вспомогательный процесс разрешения. Защита `strict_route` и настоящая HTTPS
проверка через выбранный outbound остаются включёнными.

## Reality ML-KEM в Mihomo — 17.10.2026

Для профилей с явным `support-x25519mlkem768=true` генератор Mihomo
выбирает `chrome`, сохраняя исходный fingerprint в профиле. Это общий
генератор Windows и Android sidecar. Замена отражается в журнале.
При отсутствии флага или значении false исходный fingerprint сохраняется.
Для неуспешной Windows HTTPS-проверки добавлен очищенный ответ API ядра.

Причина: Mihomo 1.19.32 закрепляет uTLS 1.8.8, где Firefox Auto — Firefox 120
без ML-KEM. Флаг Reality не добавляет недостающий key share. Источники:
[go.mod](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/go.mod),
[uTLS](https://github.com/MetaCubeX/utls/blob/v1.8.8/u_common.go),
[Reality](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/component/tls/reality.go).

Проверки:

- `tests/test_mihomo_reality_handshake.py`: 2 passed. Настоящий комплектный
  Mihomo отправляет ClientHello локальному TCP-приёмнику. С прежним
  `firefox` key_share X25519MLKEM768 отсутствует; после преобразования
  присутствует и предшествует X25519. Внешняя сеть не используется.
- `tests/test_mihomo.py tests/test_parser.py tests/test_share_compatibility.py
  tests/test_windows_core.py`: 208 passed. Включены реальные проверки
  конфигураций, TCP/XHTTP Reality-туннели с Xray, HTTPS-проверка, передача
  данных, счётчики и очистка. Системный прокси заменён тестовым объектом.
- `tests/test_ui_switching.py tests/test_android_bridge.py tests/test_routing.py`:
  60 passed. Проверены переключение сервера, локальный Android sidecar с
  TCP и UDP DNS и маршрутизация. Всего в трёх запусках: 270 passed.

Удалённый сервер пользователя и новые EXE/APK-сборки этой проверкой
не подтверждены. Ранее созданные бинарные пакеты содержат прежний код.
